# 演示脚本 — Demo Script

本文档提供 nano_finance 项目演示时的完整脚本，包含操作步骤与建议旁白。适用于面试展示、技术分享、项目答辩等场景。

---

## 开场白（1 分钟）

**旁白**：

> nano_finance 是一个端到端的中文金融领域大模型与 RAG 检索增强系统，基于 Andrej Karpathy 的 NanoChat 训练框架构建。
>
> 项目的核心命题是：**在不能依赖大模型数学推理的约束下，如何构建一个可验证的金融问答系统？**
>
> 我们的方案是将系统拆分为四个独立层：模型生成、混合检索、确定性计算、以及接地校验。每一层的正确性都可以独立验证。
>
> 今天我们通过 5 个场景来展示系统如何工作。

---

## 场景一：财务报告问答

### 操作（30 秒）

上传一份中文财务报告 PDF，在对话框中输入：
> "该公司2024年的营业收入是多少？"

### 旁白（1 分钟）

> 第一个场景演示最基础的 RAG 问答流程。
>
> 用户上传一份财务报告 PDF 后，系统通过 ChromaDB 的 Dense 向量检索和 BM25 稀疏检索双路召回，再用 RRF 融合和 Reranker 重排序，找到最相关的文档片段。
>
> 关键点是：**每一个回答都附带来源引用**——包括文档名、页码和 chunk ID。用户点击引用可以直接跳转到原始文档的对应位置。
>
> 这不是一个"黑箱"回答，而是**可追溯、可验证**的回答。

### 追问（30 秒）

> "与2023年相比，营业收入变化了多少？"

**旁白**：

> 系统保持会话上下文，在同一份文档中查找到 2023 年和 2024 年的数据。注意接下来系统将把这个问题路由到 Calculator 而不是 LLM 来做计算——这正是场景二要展示的内容。

---

## 场景二：确定性财务计算

### 操作（45 秒）

依次提问：
> "该公司2023年到2024年的营业收入增长率是多少？"
> "该公司2024年的毛利率是多少？"
> "该公司2024年的资产负债率是多少？"

### 旁白（2 分钟）

> 这是本系统最核心的设计决策之一：**财务计算不走 LLM，走确定性 Calculator。**
>
> 为什么不走 LLM？因为 LLM 是概率模型，做数学运算本质上是"猜"——1.4B 参数的模型算对数乘法都可能出错。在金融场景中，一个百分点的误差可能导致严重后果。
>
> 我们的 Calculator 使用 Python 的 `Decimal` 类型实现，共支持 9 种金融操作：差值、增长率、占比、求和、平均值、毛利率、净利率、负债率、单位换算。
>
> 更重要的一点：**所有操作数必须绑定到文档证据**。增长率的分子和分母分别来自文档的哪一页、哪一个数据块，系统都有明确记录。这确保了每一条数值计算都可以被审计。
>
> Calculator 的另一个关键约束是 **fail-closed 设计**：如果操作数缺少证据绑定，系统不会 fallback 到 LLM 做自由计算，而是直接阻断。这在场景三中演示。

## 场景三：单位/期间歧义阻断

### 操作（45 秒）

输入歧义问题：
> "该公司收入增长了多少？"

系统返回阻断消息。

再输入：
> "与去年相比，利润变化了多少？"

系统再次阻断。

最后输入明确的问题：
> "该公司2023年到2024年的营业收入增长率是多少？"

系统正常返回结果。

### 旁白（1.5 分钟）

> 这个场景展示 Validation 层的一个重要功能：**歧义阻断。**
>
> 第一个问题——"增长了多少"——没有指明是绝对差值还是百分比增长。系统中有 `difference` 和 `growth_rate` 两个操作，不能替用户做选择。
>
> 第二个问题——"与去年相比"——在多年度文档中，"去年"的指代不明确。
>
> 这体现了我们设计上的一个原则：**宁可拒绝回答，也不猜测用户意图。** 这与许多通用对话 AI 不同——它们会尝试猜测并直接给一个答案。在金融场景中，这种做法风险太大。
>
> 注意：一旦用户把问题明确后，系统立即可以正常计算。这不是一个"不会做"的问题，而是一个"不能猜"的问题。

## 场景四：不可回答问题安全拒绝

### 操作（45 秒）

输入：
> "苹果公司2024年的营业收入是多少？"
> （当前文档不包含苹果公司信息）

系统返回拒绝消息。

再输入：
> "该公司明年预计增长率是多少？"
> （文档不包含未来预测数据）

系统再次拒绝。

### 旁白（1.5 分钟）

> 这个场景展示了 **Answerability 校验**——系统首先判断当前索引中的文档是否足以回答用户的问题。
>
> 如果一个问题的答案不在已上传的文档中，系统应该明确告知用户："当前文档中没有相关信息"，而不是编造一个答案。
>
> 这在技术上并不复杂，但在产品安全上至关重要。通用 LLM 在面对超出知识范围的问题时，往往会产生"幻觉"——编造看似合理但完全虚假的答案。在我们的三层校验体系（Answerability → Grounding → Validation）中，这类问题在第一关就会被拦截。
>
> 当然，我需要强调：**这套系统不能保证完全消除幻觉**。Validation 是 best-effort 设计，通过减少不受支撑的输出来降低风险，但不能承诺零幻觉。这是需要向用户坦率说明的局限性。

## 场景五：在线三服务状态检查

### 操作（1 分钟）

在终端中依次运行：
```bash
bash scripts/deploy/status.sh       # 查看三服务状态
python scripts/deploy/healthcheck.py  # 健康检查
curl http://127.0.0.1:18001/health    # Model 服务
curl http://127.0.0.1:18002/healthz   # Backend 服务
curl -I http://127.0.0.1:18003        # Frontend 服务
```

然后展示 SSH 隧道访问：在本地浏览器打开 `http://127.0.0.1:18003`。

最后演示重启：
```bash
bash scripts/deploy/restart_all.sh
python scripts/deploy/healthcheck.py  # 全部通过
```

### 旁白（2 分钟）

> 最后一个场景展示的是在线部署架构。
>
> 整个系统由三个服务组成：Model 服务在 18001 端口、Backend 在 18002、Frontend 在 18003。请求链路是 Browser → Frontend → Backend → Model。
>
> 这个部署有一个特别的约束：所有服务运行在一台大学服务器上，**没有 root 权限、没有 Docker、没有 systemd**。这意味着我们不能用任何一个"标准"的生产部署方式。
>
> 我们的解决方案是：三个服务分别运行在 tmux 会话中，由 shell 脚本管理生命周期。所有端口绑定到 127.0.0.1，不暴露到公网。远程访问通过 SSH 隧道实现。
>
> Phase 7 的验收测试是 **42/42 全部通过**——覆盖了从启动顺序、端口绑定、健康检查、冒烟测试、SSE 流式输出、到重启恢复和 SSH 登出持久性的完整验收。
>
> 部署冒烟测试 **12/12 全部通过**——包括正常问答、财务计算、不可回答安全拒绝、SSE 端点和重启恢复。
>
> 整个系统的自动化测试超过 **2,000 条**，零失败——tests/、finquery_rag/backend/tests/ 下的所有 pytest 全部通过。

## 结束语（30 秒）

**旁白**：

> 以上就是 nano_finance 的 5 个演示场景。
>
> 总结一下我们做的选择：不训练原生 Function Calling，而是用系统编排实现工具调用；不让 LLM 做数学计算，而是用确定性 Calculator；不信任单一检索，而是融合 Dense + BM25 + Reranker；不是简单做回答，而是三层校验 + fail-closed 安全降级。
>
> 每一个设计选择背后都有一个明确的原因。欢迎大家提问。

## Q&A 准备

以下常见问题已准备好回答话术，详见 [interview-guide.md](interview-guide.md)：

1. 为什么重训 tokenizer？——中英文混合 + 金融语料，原生 tokenizer 不适用
2. 为什么不让 LLM 直接做财务计算？——概率模型数学不可靠，用确定性 Decimal 替代
3. 如何确保操作数来自文档？——证据绑定 + Validation 校验
4. 为什么融合 Dense 和 BM25？——语义匹配 + 关键词精确匹配互补
5. Validation 和 prompt 约束有什么不同？——prompt 是软约束，Validation 是硬阻断
6. 为什么只有一次修复尝试？——避免无限循环，fail-closed 设计
7. 为什么不用原生 Function Calling？——没训练过，不声称支持
8. 如何防止 eval 标签泄漏到生产代码？——评估隔离机制
9. 如何无 root 部署三个服务？——tmux + shell 脚本 + 127.0.0.1 绑定 + SSH 隧道
10. 当前系统最大的局限是什么？——模型不可复现验证 + 无自动重启 + 无水平扩展

## 演示注意事项

- **不要声称**"模型支持原生 Function Calling"——Calculator 是系统编排
- **不要声称**"系统消除了幻觉"——Validation 是 best-effort，不能完全消除
- **不要声称**"生产级精度"——0/54 结果不是质量指标
- **不要声称**"tokenizer 带来 X 倍提速"——压缩率不等于推理速度
